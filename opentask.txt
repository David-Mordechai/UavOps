## Where we actually are (as of this session, 2026-09-06)

Model is now **`Qwen/Qwen3.8-27B-FP8`** (dense, official Qwen org, FP8, ~28.5GB), served via vLLM,
container `vllm-qwen3.8-27b-fp8`, port 8000, same host `192.168.1.155`. Launch flags:
`--max-model-len 65536 --gpu-memory-utilization 0.8 --enable-auto-tool-choice --tool-call-parser
qwen3_xml --reasoning-parser qwen3 --enable-prefix-caching --default-chat-template-kwargs
'{"enable_thinking": false}' --override-generation-config '{"temperature": 0}'`. This replaced
`nvidia/Qwen3.6-35B-A3B-NVFP4` (the model the previous opentask.txt's investigation was about) —
`appsettings.json`'s `AgentModels` section now points every agent at the new model.
`OpenAI:Endpoint` is `http://192.168.1.155:8000/v1`.

**Headline conclusion (see "Decisive experiment" below): the model itself is reliable at this
whole task. The multi-agent architecture (BrainAgent → MoavAgent → leaf agents, with natural-
language instruction rewriting at each hop, forced tool_choice, and shared disambiguation state)
is what's introducing the failures observed live. This was not obvious going in — most of this
session was spent (correctly, but not sufficiently) chasing what looked like backend/model
unreliability, until a clean single-agent baseline proved the model has no trouble with the exact
same task.**

## What changed this session, in order

1. **Continued the previous session's vLLM config testing** (parser swap, temp/thinking overrides)
   against `Qwen3.6-35B-A3B-NVFP4` — parser swap (`qwen3_coder`→`qwen3_xml`) made no measurable
   difference to the original leaf-fabrication bug; removing the `temperature:0`/`enable_thinking:
   false` server overrides made things measurably *worse* (~14% incomplete tool-call batches vs.
   ~1-2% before). Superseded by the model switch below — don't chase this further on the old model.

2. **User switched the served model to `Qwen/Qwen3.8-27B-FP8`** (dense, per config above). Isolated
   HTTP testing (leaf-agent-shaped tool schema, matching production's real 3-tool `FlightControlAgent`
   request) showed a clean **0/288** failure rate at 6-way concurrency — looked like a strong
   improvement over the old model. `appsettings.json`'s `AgentModels` updated to match (done this
   session, no code changes needed — provider/endpoint plumbing already supported this).

3. **User then live-tested via the real chat UI** and hit a *worse* class of bug than anything in
   the old model's history: **BrainAgent itself never called `CreatePlan` at all** for a real
   "fly all of them to target alpha..." fleet command — zero tool calls, zero reasoning trace,
   a fully confident, fully fabricated "All done, David" success report. This is the router-tier
   fabrication CLAUDE.md's *old* content had flagged as a "known open issue" theoretically covered
   by `RequireToolOnFirstTurnChatClient` — that forcing did not hold here.

4. **Implemented, tested, and fixed two things** (both still in place, both validated):
   - **`MainAgentOrchestrator` verified-retry safety net**: after every `BrainAgent` completion,
     checks `ToolInvocationLogger.GetAgentInvocationCount(correlationId, "BrainAgent")` (BrainAgent's
     only tool is `CreatePlan`, so any count > 0 means a real call happened, even an empty-steps
     one). Zero count → roll back the persistent session's history to before this attempt (via
     `InMemoryChatHistoryProvider.GetMessages`/`SetMessages` snapshot/restore) and retry, up to 3
     attempts total. If all 3 fail, return an honest failure message instead of fabricated text.
   - **Serilog file sink** added (`Program.cs`, `logs/uavops-agent-*.log`, `.gitignore` updated) so
     future incidents don't need manual chat-UI copy-paste to diagnose.
   - **Bug found and fixed in the retry design itself, same session**: the first version wrote the
     honest-failure sentence into BrainAgent's *actual persistent history*. Proven via direct A/B
     (10/10 clean history → real `CreatePlan` call, vs. 0/10 with that sentence sitting in history →
     every later turn, regardless of what was asked, came back as that exact sentence verbatim,
     zero tool calls) that this is a **degenerate repetition trap** — an unusual, templated
     assistant utterance in context makes the model get "stuck" repeating it. Fixed: a failed turn
     now leaves **zero trace** in BrainAgent's history (not even the operator's own message).

5. **Confirmed via direct backend testing, decisively, that certain content deterministically
   breaks forced tool-choice on this model** — not a rare flake. A bare greeting
   ("hi my name is David...") with `tool_choice: "required"` (tested both the generic string form
   and a named-function-choice form) failed **15/15**, byte-identical output each time at temp 0,
   even with a maximally trivial one-field dummy schema (ruling out `CreatePlan`'s schema
   complexity as the cause). This is a genuine backend/model ceiling for conversational content,
   not fixable from application code. The retry safety net's fallback message was reworded to stay
   accurate for this case (doesn't presume a command was involved).

6. **Verified byte-for-byte that the app's actual outgoing HTTP request matches manual test
   reconstructions** — captured the real request via a `HttpClientPipelineTransport`-wrapped
   `HttpClient` swapped into the same `chatClientFactory` code path `Program.cs` uses (temporary
   test, since deleted — `RealRequestCaptureTests.cs`). Confirmed `"tool_choice":"required"` really
   is on the wire, plus two fields the earlier manual Python repro scripts never included
   (`"temperature":0.2` — from `BrainAgent.yaml`'s own config, since the server's
   `override-generation-config` doesn't override every field as hoped in every measurement — and
   `"parallel_tool_calls":true` — from `AllowMultipleToolCalls`). Neither field, once matched
   exactly in isolated replay, changed the outcome for either the greeting case (still 0/32) or the
   "fly all" case (still ~100% success in isolation) — ruled out as an explanation for the gap
   between clean isolated tests and flakier live behavior.

7. **User pushed back hard** ("I need a reliable agent system... not your safety nets"), explicitly
   rejected a cloud-model option for `BrainAgent` (must stay fully offline/local), and directed
   live testing via the actual browser chat UI (Claude-in-Chrome), not synthetic scripts.

8. **Live UI testing found the real, precise, structural bug** (not model-forcing unreliability):
   - `MoavAgent` delegated to `PayloadControlAgent` using the pronoun **"their"** — *"Point their
     payloads at target alpha."* — instead of restating "every UAV" explicitly, directly violating
     an already-existing anti-pronoun rule in `MoavAgent.yaml` that just wasn't followed strongly
     enough.
   - Because of the missing trigger word, `PayloadControlAgent` couldn't recognize the fleet-wide
     scope and asked "Which UAV do you mean?" — a genuinely ambiguous question given what it was
     handed, not a fabrication.
   - The operator's answer ("UAV-1") got cached in `TailNumberResolutionScope` — shared across the
     **entire turn**, all specialists, by design (see point 9).
   - `FlightControlAgent`, working from a correctly-worded instruction ("fly all of them..."),
     tried to resolve "ALL" — but because the scope already had an answer cached from the
     *unrelated* payload question, it silently reused "UAV-1" instead of asking its own legitimate
     "apply to all 3?" confirmation.
   - Net result: only UAV-1 actually moved (real tool calls, real state mutation — this is NOT a
     zero-invocation case, so the existing safety net doesn't catch it), but `FlightControlAgent`'s
     own summary said "I'll send all UAVs... UAV-1 is now flying," `MoavAgent` compounded that into
     "All UAVs are flying," and `BrainAgent` relayed a fully false "All UAVs are now flying to
     alpha... with their payloads pointed at alpha" to the operator. Confirmed via the real
     `ToolInvocationLogger` trace and the real `SimulatedUavOperationService` state (UAV-2/UAV-3
     untouched, still at defaults).

9. **`TailNumberResolutionScope`'s whole-turn sharing is a *deliberate* prior design decision, not
   an oversight** — `AgentFactory.cs`'s own comment says a per-agent scope was tried before and
   caused the *same* "apply to all 3?" confirmation to be asked twice (once per specialist), which
   was worse UX. **Did not rewrite this mechanism this session** given that documented regression
   risk and the lateness of the finding — instead fixed the actual trigger (next point). If the
   cross-specialist conflation bug resurfaces from some other cause, revisit this deliberately,
   not hastily — the fix needs to distinguish "the model explicitly recognized ALL" from "the model
   made an ungrounded single-UAV guess" as different dedup buckets, without reintroducing the
   double-prompt regression.

10. **Fixed the actual trigger**: strengthened `MoavAgent.yaml` (anti-pronoun rule extended to
    cover collective/"their"-style references explicitly, plus a new rule against inventing
    "confirm before executing" framing in delegate instructions) and `BrainAgent.yaml` (same
    "never add your own confirm-before-executing wording" rule, since BrainAgent was independently
    doing the same thing one level up, in its own `CreatePlan` step instructions to `MoavAgent`).
    Both edits include concrete negative examples matching exactly what went wrong, per this
    codebase's established style.

11. **Verified live through the actual browser UI, twice** — first run (before the fix) reproduced
    the false "all done" claim end-to-end with the real trace showing only UAV-1 touched; second
    run (after rebuild+restart) showed the *correct* deterministic "Apply this to all 3 known UAVs
    (UAV-1, UAV-2, UAV-3)? Yes/No" confirmation firing, and after confirming, all 9 real tool calls
    (`Navigate`/`SetSpeed`/`SetAltitude`/`PointPayload` × 3 UAVs) executed correctly with an
    accurate final summary matching real state.

12. **Remaining known-but-unfixed issues, for awareness**:
    - The greeting still deterministically fails to call `CreatePlan` (point 5 above) — safety net
      catches it cleanly (honest failure, no false claim), but it's a real, unresolved UX cost
      (~10s wasted per greeting) with no app-side fix available against this model/backend.
    - `TailNumberDisambiguationTool`'s "which UAV do you mean?" prompt is missing the "ALL" button
      its own code (`TailNumberDisambiguationTool.cs` line ~130,
      `tails.Select(t => t.TailNumber).Append(AllSentinel).ToList()`) should be offering as a 4th
      choice — observed live (only UAV-1/2/3 buttons rendered). Not investigated further — could be
      a chat.js rendering issue or something in how `OperatorPromptGate`/`AskOperatorChoiceTool`
      passes the choices list through. Worth a quick look next session.
    - `BrainAgent`'s router-tier judgment for "What UAVs do we have?" is inconsistent — observed
      it twice choosing an **empty** `CreatePlan` (no delegation) and asking the operator "want me
      to check?" instead of just calling `MoavAgent`, even though nothing in its own history could
      answer the question. Not a fabrication (no false claim, it's honest that it doesn't know) but
      a real judgment/routing quality issue, separate from everything else fixed this session — not
      investigated or fixed.

13. **Decisive experiment, per explicit user request** ("I want to be sure this is not our service
    design issue"): built a **fully independent, single-agent Python baseline**
    (`single_agent_test.py`, path below) — one flat agent, all 6 tools exposed directly (no
    BrainAgent/MoavAgent/leaf split, no delegation, no natural-language instruction hand-off
    between agents, no `TailNumberResolutionScope`), a tiny in-memory fake 3-UAV fleet, talking
    directly over raw HTTP (no .NET, no Microsoft.Extensions.AI, no OpenAI SDK — zero possibility
    of any app-level bug touching this) to the **same real backend** (`Qwen/Qwen3.8-27B-FP8`).
    Replayed the *exact* 3-turn conversation (introduce self → "what UAVs do we have?" → "fly all
    of them to target alpha and set speed to 250 and altitude to 3000 to all of them also point
    there payloads there") **8 independent times**, fresh fleet state each run, `tool_choice:
    "auto"` (not forced — a normal single-agent design has no reason to force it for a greeting).
    **Result: 8/8 fully correct.** Every run: correct self-introduction with no spurious tool call,
    correct `ListFleet` call and accurate 3-UAV summary, then all 12 correct tool calls in a single
    round (`Navigate`+`SetSpeed`+`SetAltitude`+`PointPayload` × UAV-1/UAV-2/UAV-3, right values,
    right tail numbers) with a final summary matching real ground-truth fleet state exactly every
    time. Full raw output for 3 of the 8 runs (5, 6, 7) plus the aggregate line is preserved in
    this session's transcript; script and env are still on disk (see below).

## Conclusion reached this session

**The model is not the bottleneck. The multi-agent architecture is.** A flat, single-agent design
with tools exposed directly, no forced tool-choice on conversational turns, no natural-language
instruction rewriting between agents, and no shared cross-specialist disambiguation state gets
this exact task right reliably (8/8). The real app's multi-hop design (`BrainAgent` → `MoavAgent`
→ per-domain leaf agents, `CreatePlan`'s forced single-tool-choice, instructions re-synthesized in
free text at every hop, `TailNumberResolutionScope` shared across an entire turn) is what
introduces the failure surface — the pronoun bug (point 8), the router-tier zero-call fabrication
(point 3), and the deterministic greeting refusal (point 5) are all consequences of hops and
forcing that a flatter design wouldn't have in the same shape.

**This does not mean today's fixes were wasted** — the verified-retry safety net and the
pronoun/confirm-wording instruction fixes are real, validated improvements to the *current*
architecture, and should stay regardless of what happens next. But the user's own framing is
correct: the ceiling on reliability here is architectural, not (primarily) a model-quality problem
that swapping models again would fix on its own — *unless* a materially different model turns out
to be dramatically more robust to the specific things this architecture stresses (multi-hop
instruction fidelity, tolerance for forced tool-choice on low-content turns). That's exactly what
tomorrow's first step should check.
